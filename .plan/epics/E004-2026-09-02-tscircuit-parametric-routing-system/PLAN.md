# E004: Parametric TS Circuit carrier-board system

## Goal

Turn the E003 carrier-board candidates into a reusable TypeScript system. A
new board variant should be defined by typed configuration and reusable
components, not by copying a large JSX file. The same source must produce the
component tree, schematic connectivity, PCB placement, routed traces,
verification report and review portal.

## Why now

E003 proves the footprint and review pipeline, but its current implementation
still mixes four responsibilities in board files. Variant A contains manually
written traces; B, C and D contain footprints and review notes without a
complete PCB netlist or copper routing. Placement values are also repeated as
inline coordinates. This makes a change easy to apply to one variant and miss
in the others.

## Desired outcome

- one reusable component library with explicit evidence and pin contracts;
- one typed variant model for A, B, C and D;
- one canonical netlist per variant, with required, optional and intentionally
  unconnected pins represented explicitly;
- placement expressed through anchors and constraints instead of scattered
  magic coordinates;
- routing generated by a controlled adapter: automatic where safe, explicit
  where critical, and always verified;
- a hard failure for missing required connections or unrouted required nets;
- generated artefacts and the review portal produced from the same resolved
  design model;
- a functional core that can resolve and validate boards without React,
  filesystem, network or renderer access;
- typed physical units and named coordinate datums for components and boards;
- one versioned resolved-design schema with a computed, monotonic maturity gate;
- an impact report showing which variants, nets and artefacts changed after a
  component, rule or evidence update;
- a documented extension path for a future board variant without copying
  existing board source.

## Scope

### In scope

- refactoring `hardware/e003-carrier` into typed domain, component, board,
  routing and verification layers;
- reusable footprints for received modules, JLCPCB parts and local provisional
  support parts;
- variant configuration for A/B/C/D;
- power, ground, I2C, USB, QSPI, clock, interrupt and buzzer net contracts;
- two-layer placement and routing with explicit critical-net policy;
- tscircuit autorouter integration as a constrained proposal mechanism, with a
  deterministic local/manual fallback;
- connectivity, route, clearance, keep-out, board-edge and provenance checks;
- regression fixtures proving that a fifth variant can be added by composition;
- review portal changes that expose net status, route status and provenance.

### Out of scope

- changing the desktop application, firmware or USB/wireless protocol;
- fabricating or ordering a PCB;
- claiming the received ToF module geometry is measured before evidence exists;
- hiding an uncertain footprint behind a generic component name;
- making the autorouter the final authority for RF, clocks, power or safety;
- replacing TS Circuit with KiCad unless the export or routing gates prove that
  TS Circuit cannot express the required board.

## Architecture boundary

```text
physical evidence / vendor sources / JLC catalogue
                 │
        source-backed PartSpec + PinSpec
                 │
      product-neutral component primitives
                 │
    E003 CarrierVariant + typed NetContract
                 │
 placement plan → routing plan → ResolvedBoardDesign v1
                 │                         │
      maturity + impact report      tscircuit / router adapters
                 │                         │
        checks / portal         Circuit JSON / SVG / export
```

| Capability | Owner | Consumers | Boundary status |
|---|---|---|---|
| Evidence, source URL, revision, confidence | `evidence/` | component library, reviewer | stable |
| Pad geometry and named ports | `src/components/` | board generator, verifier | stable |
| Product variant vocabulary | `src/domain/` | board recipes, tests, portal | stable |
| Board-specific placement and electrical rules | `src/boards/` | resolver, router | provisional until review |
| Physical units and coordinate transforms | `src/domain/geometry/` | placement, routing, checks | stable |
| Resolved design schema and maturity evaluator | `src/domain/resolved/` | all adapters and reports | stable and versioned |
| Routing algorithm | `src/routing/` adapter | board resolver, verifier | provisional; provider may change |
| SVG/JSON/portal rendering | scripts and portal | human reviewer | edge adapter |
| Firmware/application behavior | separate product repo | hardware test harness | explicitly deferred |

Shared primitives remain product-neutral. Hardware-specific names such as
`VDD_3V3`, `I2C_SDA` and `BUZZER_DRV` belong to the carrier domain and must not
leak into generic footprint helpers. The renderer consumes resolved outputs; it
must not invent electrical or mechanical rules.

## Design rules

1. Prefer composition and typed factories over class inheritance. A feedback
   board is a base carrier plus capabilities, not a subclass with duplicated
   wiring.
2. Treat the netlist as the electrical source of truth. JSX traces are an
   output of the routing layer, not the place where connectivity is invented.
3. Treat evidence as separate from inference. Every provisional field remains
   visible in the source register and blocks fabrication when required.
4. Use autorouting for repeatable initial solutions and explicit constraints;
   review or lock critical routes manually.
5. Make invalid states hard to represent where practical: discriminated
   variants, typed endpoint names, required-net assertions and explicit NC pins.
6. Every generated variant goes through the same render, route, verify and
   portal pipeline.
7. Keep a pure functional core and move React, tscircuit, filesystem, network
   and portal concerns to adapters at the edge.
8. Use typed physical units and named datums; raw provider unit strings belong
   only in adapters.
9. Compute board maturity from evidence and gate results. No script or UI may
   promote a board by setting a status label directly.
10. Generate a semantic design diff so a source or component change lists its
    affected variants, nets, placement, routes and review artefacts.

## Acceptance criteria

- [ ] A/B/C/D are generated by one board factory and typed configuration;
      variant files contain no copied board trees.
- [ ] Components expose stable named ports, pad maps, geometry and provenance;
      local provisional parts are isolated and replaceable.
- [ ] Each variant has a canonical netlist covering all required power,
      ground, bus, control, clock, memory and feedback connections.
- [ ] `npm run verify:boards` fails on an injected missing endpoint, missing
      required trace, unrouted net, illegal collision or off-board route.
- [ ] B/C/D show actual routed copper in their PCB renders, with route counts
      and net status visible in the report.
- [ ] Critical nets have layer/width/clearance/keep-out policy and are either
      locked explicitly or accepted by the routing review.
- [ ] A regression fixture can create a fifth composition-based variant without
      modifying the component implementation or verifier.
- [ ] Generated artefacts, manifest and portal remain deterministic and contain
      the resolved net/routing status.
- [ ] The pure domain resolver can produce A–D `ResolvedBoardDesign` fixtures
      without loading React, tscircuit, filesystem or network modules.
- [ ] Geometry uses typed millimetre/angle values and explicit component/board
      datums; unit conversion exists only at adapter boundaries.
- [ ] Maturity is derived from one versioned schema and cannot skip unresolved
      evidence, geometry, netlist, route, check or human-review gates.
- [ ] Every generated change includes a semantic impact report for affected
      variants, components, nets, routes and artefacts.
- [ ] `npm run check` passes and the browser portal has zero console errors.
- [ ] The fabrication gate remains closed until physical evidence, exact
      footprints, manufacturing export and qualified human review are complete.

## Test strategy

- unit tests for `PartSpec`, pin maps, variant discriminated unions and net
  contracts;
- negative fixtures for missing endpoints, duplicate net ownership, illegal
  NC claims, unrouted required nets and unsupported router output;
- geometry fixtures for pad/trace/hole/keep-out/board-edge collisions;
- deterministic snapshot/hash checks for resolved netlists and route plans;
- schema compatibility, maturity-transition and typed-unit fixtures;
- semantic design-diff fixtures for component, evidence and routing changes;
- four-variant render and portal browser QA;
- manual review of critical power, USB, QSPI, clock, I2C and RF routes;
- no fabrication approval from automated output alone.

## Execution waves

1. **Foundation:** freeze current behaviour, define boundaries and establish
   typed contracts.
2. **Reuse:** extract components, evidence adapters and variant configuration.
3. **Electrical model:** implement canonical netlists and resolve all required
   endpoints.
4. **Physical model:** implement anchors, constraints and two-layer routing.
5. **Migration:** move A/B/C/D to the factory and remove duplicated board trees.
6. **Release gates:** enforce verification, regenerate portal and document the
   extension workflow.

## Definition of done

The system can generate all four variants from shared typed building blocks,
produce real routed PCB candidates, prove required connectivity and geometry,
and publish a reviewer-readable report. The output is still a review
candidate; fabrication requires the existing physical-evidence and qualified
external-review gates.
